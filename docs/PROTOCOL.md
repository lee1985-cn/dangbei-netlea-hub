# 尼特利滤桶 BLE 协议（实测验证版）

来源：微信小程序 `wx9bc9d96d33726145` 反编译（PC 微信 4.x，V1MMWX 加密 → AES-256-CBC 解头 + 单字节 XOR 解体）
**实测设备**：尼特利 1 号变频过滤桶（20 档），广播名 `NL NO.1S-G1`，MAC `34:00:80:E3:BB:81`

> 本文档的字节布局已经**在真实设备上验证过**（写入档位 → 读回确认），不是纯静态分析。

---

## 1. GATT 服务与特征（实测枚举结果）

服务 UUID：

```
0003CBBB-0000-1000-8000-00805F9BFFF0
```

实测该服务下的全部特征值：

| 特征 | 属性 | 用途 |
|---|---|---|
| `...9BEEE1` | read + writeNoResponse | 控制写入（开关/档位/喂食） |
| `...9BEEE2` | read + writeNoResponse | 行程表写入（106 字节） |
| `...9BEEE4` | read + writeNoResponse + **notify** | 状态通道：可 GATT 读，也可写 `02 02` 触发上报 |
| `...9BEEE5` | read + writeNoResponse | 语音 / 切回蓝牙控制 |
| `...9BEEEF` | read + writeNoResponse | 保留 |

**关键**：所有特征值都支持 `read`，`write` 一律用 **writeNoResponse**（不支持带响应写）。

小程序代码里还兼容 `DDD1~DDD6`、`FFE1~FFEF` 系列（按后缀 `indexOf` 模糊匹配），说明同一套 App 适配多个 OEM 模组。本设备是 **EEE 家族**。

## 2. 帧格式（校验 + XOR 混淆）

```python
KEY = [76,101,100,115,38,70,117,110]   # ASCII "Leds&Fun"

def crc(data):            # 自定义 8 位移位 XOR 校验
    n = 0
    for b in data:
        r = b
        for k in KEY:
            if r & 1: n ^= k
            r = (r >> 1) & 0xFF
    return n & 0xFF

def encode(data):         # 发送
    t = crc(data)
    return bytes([t] + [t ^ b for b in data])

def decode(frame):        # 接收
    t = frame[0]
    data = bytes([t ^ b for b in frame[1:]])
    return data if crc(data) == t else None
```

首字节是校验值，其余每字节 = 校验值 XOR 明文。**无配对、无加密、无绑定**。

## 3. 控制命令（写到 EEE1）

明文 12 字节，编码后 13 字节：

```
[0] = 0x02        固定：水泵类
[1] = onOff       1=开 0=关
[2] = 0
[3] = 0x01
[4] = 0x01
[5] = model       1=纯档位 2=档位+流量 3=喂食(用 timing) 6=关机时强制
[6] = gear        档位 1~20
[7] = level       流量等级（model=2 用）
[8] = timing      喂食分钟（model=3 用）
[9] = 0
[10..11] = 0x58 0x02
```

`onOff == 0` 时 model 强制为 6。

### 实测帧

| 动作 | 明文 | 发送帧（13B） |
|---|---|---|
| 开 8 档 | `02 01 00 01 01 01 08 00 00 00 58 02` | `53 51 52 53 52 52 52 5b 53 53 53 0b 51` |
| 开 9 档 | `02 01 00 01 01 01 09 00 00 00 58 02` | （实测生效） |
| 开 20 档 | `02 01 00 01 01 01 14 00 00 00 58 02` | `62 60 63 62 63 63 63 76 62 62 62 3a 60` |
| 关机 | `02 00 00 01 01 06 08 00 00 00 58 02` | `52 50 52 52 53 53 54 5a 52 52 52 0a 50` |
| 喂食 20 分钟 | `02 01 00 01 01 03 00 00 14 00 58 02` | `07 05 06 07 06 06 04 07 07 13 07 5f 05` |
| 读状态 | `02 02` | `00 02 02`（写到 **EEE4**） |
| 切回蓝牙控制 | `02 04` | `01 03 05`（写到 EEE5） |

## 4. 状态帧（实测，9 字节编码 → 8 字节明文）

实测原始帧（8 档运行时）：

```
16 14 17 17 1e 16 16 16 16
```

解码 → `02 01 01 08 00 00 00 00`

**实测布局**：

```
[0] = 0x02      固定
[1] = 电量      charge（实测 1）
[2] = 电压      electric（实测 1）
[3] = 档位      ★ 实测确认（8 档时=8，设 9 档后变 9）
[4] = 流量等级  level
[5] = 保留
[6] = 工作模式  workModel
[7] = 错误码    errorCode
```

> ⚠️ **小程序里读的是 `getInt8(4)` 当档位，实测是 `[3]`。** 原因不明（可能是不同模组版本），以实测为准。这是本项目相对静态分析的一处修正。

工作模式取值（来自小程序）：`1`=档位 `2`=档位+流量 `3`=喂食设置 `5`=喂食中 `6`=关 `7`=**自吸排气**。

### 读状态的两种方式（实测都可用）

1. **GATT read EEE4** —— 最简单，直接拿 9 字节，无需订阅
2. **写 `02 02` 到 EEE4 → 等 notify** —— 小程序的做法，设备会主动上报同一帧

## 5. 重要行为约束（实测）

1. **自吸排气期禁控**：开机后 30 秒 ~ 15 分钟（workModel=7）设备拒绝蓝牙控制，自动化要等状态变 1。
2. **单连接**：同一时刻只能有一个 BLE 主机。ESP32 连着时手机小程序连不上，反之亦然。
   → 固件采用**长连接 + 空闲 20 秒自动断开**，兼顾命令响应速度和让出连接。
3. **连接有概率失败**：设备对快速连断不友好，必须带重试（实测 3 次重试可稳定）。
4. **无配对**：不需要 bonding，连上即可读写。
5. **地址类型**：本设备是 `BLE_ADDR_PUBLIC`（type=0）。扫描时应记录 `getAddress().getType()` 并优先使用。

## 6. 踩过的坑（给后来人）

### `#define USE_NIMBLE` 必须是全局编译参数

写在 `.ino` 顶部**无效**——Arduino 单独编译每个库，宏不会传给 `BleKeyboard.cpp`。结果是：
- BleKeyboard 用 Bluedroid，滤桶客户端用 NimBLE
- 两个蓝牙栈并存，NimBLE 根本没被初始化（`getInitialized()==0`）
- 所有扫描/连接静默失败，且串口毫无提示

正确做法：

```bash
arduino-cli compile --build-property "compiler.cpp.extra_flags=-DUSE_NIMBLE" ...
```

PlatformIO 里 `build_flags = -DUSE_NIMBLE` 是全局的，没这个问题。

### `setConnectTimeout()` 的参数是 uint8_t（秒）

`setConnectTimeout(5000)` 会被截断成 136，实际等 136 秒。要写 `setConnectTimeout(5)`。

### 只刷 app，不要覆盖 bootloader

用 `arduino-cli` 编出来的 `bootloader.bin` 和板子上原有的**不是同一个构建**。刷了会进入无限重启（`rst:0x3` 循环，串口只有 ROM 横幅）。

正确做法：只写 app。

```bash
esptool.py --port /dev/ttyACM0 write_flash --flash_mode dio --flash_freq 80m --flash_size 4MB \
  0x10000 app.bin
```

分区表原厂和 arduino 编出来的**完全一致**（已逐字节比对），所以不用动。

## 7. 喂食状态实测（补充）

真机（NL NO.1S-G1）实测的状态帧在喂食期间变化：

| 状态 | 明文帧 | 说明 |
|---|---|---|
| 正常运行 8 档 | `02 01 01 08 00 00 00 00` | |
| 喂食 10 分钟中 | `02 01 03 00 00 0a 00 00` | |

由此确定本模组的真实布局（与小程序读法不同）：

```
[1] = 固定 1
[2] = 工作模式   1=档位运行  3=喂食
[3] = 档位       喂食期间为 0（泵停）
[5] = 喂食剩余分钟
[6] [7] = 常为 0
```

固件已按上表修正（v2）：`model=plain[2]`、`gear=plain[3]`、`feed=plain[5]`、`err=plain[7]`。
`/filter/state` 返回 `{"gear":8,"model":1,"feed":0,...}`，`model` 取值：

| model | 含义 |
|---|---|
| 1 | 按档位运行 |
| 2 | 档位 + 流量等级 |
| 3 | 喂食中（`feed` = 剩余分钟） |
| 6 | 已关闭 |

⚠️ **关泵后 `gear` 仍会保留上次档位**（`02 01 06 08 ...`），所以判断"是否在转"必须看 `model`，
不能只看 `gear > 0`——这是 HA 开关实体一开始关泵后图标不变灰的原因。

### 取消喂食

设备**没有专门的取消命令**。小程序的做法是重发一条普通控制帧（`timing=0`），即：

```
pumpControlCMD(onOff=1, model=1, gear=当前档位, level=0, timing=0)
```

等价于我们的 `/filter/speed?n=<当前档位>`。

**关键**：喂食开始后约 **25 秒**内设备会拒绝控制命令（保护窗口），
所以取消必须延迟 25 秒再发，并重试几次。实测延迟 30 秒后发送可 100% 成功。
